# Зачем в mio C-прослойка (CMIO), а не чистый Swift

Документ объясняет, почему пакет состоит из двух целей — `MIO` (Swift) и
`CMIO` (C) — и почему «убрать C и писать всё на Swift» технически нельзя,
а обходные пути, которые существуют, хуже. Все факты ниже проверены на
реальном тулчейне (Swift 6.2.4, Linux x86_64); команды для
самостоятельной перепроверки — в §8.

Смежный документ: [ARCHITECTURE.md](ARCHITECTURE.md) — общая архитектура
и схемы операций.

---

## 1. TL;DR

C-слой — это **97 строк** (`wrapper.c` + `CMIO.h`): 1:1 проброс шести
syscall'семейств (`epoll_*`, `eventfd`, `timerfd_*`) и одна packed-
структура. Вся логика — типы, владение, ретраи, таймауты — живёт в Swift.
Слой существует из-за трёх пробелов Swift на Linux, два из которых
непреодолимы напрямую:

1. модуль `Glibc` **не экспортирует** `sys/epoll.h`, `sys/eventfd.h`,
   `sys/timerfd.h` — функций epoll просто нет после `import Glibc`;
2. в Swift **нет packed-структур**, а 12-байтовый ABI `epoll_event`
   требуется ядру;
3. (мягкая причина) чтение `errno` из Swift не имеет формальной гарантии
   отсутствия гонки.

Убрать прослойку нельзя; сделать её толще — незачем: это осознанно
«тупой» шов без единого решения, ноль runtime-оверхеда.

## 2. Что именно делает CMIO

| Функция C | Syscall | Конвенция возврата |
|---|---|---|
| `sl_epoll_create1` | `epoll_create1(EPOLL_CLOEXEC)` | `fd ≥ 0` \| `-errno` |
| `sl_epoll_ctl_add/mod/del` | `epoll_ctl` | `0` \| `-errno` |
| `sl_epoll_wait` | `epoll_wait` | `n ≥ 0` \| `-errno` |
| `sl_epoll_pwait2` | `epoll_pwait2` (NULL-timespec для «навсегда») | `n ≥ 0` \| `-errno` |
| `sl_eventfd` | `eventfd` | `fd ≥ 0` \| `-errno` |
| `sl_timerfd_create/settime` | `timerfd_*` | `fd / 0` \| `-errno` |

Плюс `sl_epoll_event` — 12-байтовая packed-зеркальная копия
`struct epoll_event` из `<sys/epoll.h>` (`events: uint32_t` +
`data: uint64_t`, в `data` ездит `Token.raw`).

Политики в C нет никакой: ни ретраев, ни fallback'ов, ни магии с errno —
только снятие errno в знак результата. Решения принимаются в Swift.

---

## 3. Причина 1 — модуль Glibc не содержит epoll (блокер)

Модуль `Glibc` в Swift — это не «весь glibc», а umbrella-заголовок
`SwiftGlibc.h` с курированным списком из 188 инклюдов. Проверка на
Swift 6.2.4:

```
$ grep -c include  .../lib/swift/linux/x86_64/SwiftGlibc.h
188
$ grep -E "epoll|eventfd|timerfd" .../SwiftGlibc.h
(пусто)
$ grep -E "signal.h|sys/socket.h|sys/select.h" .../SwiftGlibc.h
#include <signal.h>
#include <sys/select.h>
#include <sys/socket.h>
```

Отсюда наблюдаемое в тестах mio поведение: `signal`, `pthread_sigmask`,
`sigtimedwait`, `socketpair`, `shutdown`, `raise` вызываются из Swift
напрямую (они в umbrella), а `epoll_create1` и т.п. — нет, и не могут:
символов в модуле просто нет. Это не ограничение нашей фантазии, а
факт импортёра Clang: `sys/epoll.h` и соседи никогда не включались в
курированный список (modulemap помечен «semi-complete» самим Apple).

## 4. Причина 2 — packed-структура, которой нет в Swift

`struct epoll_event` в ядре — **12 байт**: `u32 events` + `u64 data`,
без паддинга (`__attribute__((packed))`). `epoll_wait(2)` пишет в буфер
вызывающего сплошные 12-байтовые записи — любой паддинг разрушает данные.

В Swift нет аналога `packed`:

```swift
struct NaiveEvent { var events: UInt32; var data: UInt64 }
MemoryLayout<NaiveEvent>.size      // 16 (!) — Swift вставил 4 байта
                                   // выравнивания под UInt64
```

Буфер из таких структур — гарантированная порча при первом же
`epoll_wait`. Обходной путь существует — три `UInt32`-поля (`events`,
`dataLo`, `dataHi`: размер 12, выравнивание 4) с ручной пересборкой
`UInt64` на каждом доступе — но это постоянный источник ошибок в самом
горячем пути ради формального «pure Swift». В C корректная структура —
одна строка с атрибутом.

## 5. Причина 3 — errno: гарантия против «почти всегда»

POSIX разрешает функциям менять `errno` и при успехе; между возвращением
syscall'а и чтением `errno` в Swift теоретически может вмешаться
рантайм (например, аллокатор потрогает `mmap`). Чтение errno в C
непосредственно после syscall'а — формально герметично:

```c
int n = epoll_wait(...);
return n < 0 ? -errno : n;   // errno снят до любого постороннего кода
```

Это мягкий аргумент (SwiftNIO читает errno из Swift и живёт), но в
сочетании с причинами 1–2 он достаётся бесплатно.

## 6. Альтернативы «без C» и почему они отвергнуты

### 6.1 `syscall(2)` напрямую

`syscall` экспортируется Glibc и вызываем из Swift (variadic C).

Минусы:
- **номера syscall'ов arch-специфичны**: `SYS_epoll_create1` = 429 на
  x86_64, но имеет другой номер на aarch64/riscv64 — нужна своя таблица
  на каждую архитектуру с риском опечатки, которую никто не проверит;
- variadic-упаковка `struct timespec` по значению (для `epoll_pwait2`) —
  работает, но хрупко и зависит от ABI-деталей;
- ноль проверок типов и сигнатур на этапе компиляции.

### 6.2 `@_silgen_name` — приватные символы libc напрямую

```swift
@_silgen_name("epoll_create1")
func epoll_create1(_ flags: Int32) -> Int32
```

Минусы:
- атрибут с подчёркиванием — **недокументированная деталь реализации**
  компилятора: без гарантий стабильности;
- линковка символа происходит **без сверки сигнатуры**: ошибка в
  объявлении = тихая порча памяти в рантайме, не ошибка компиляции;
- не решает причину 2 — packed-структуру всё равно пришлось бы
  эмулировать тройкой `UInt32`.

### 6.3 Почему C-target — не компромисс, а стандарт

SPM C-цели первоклассны; clang-компонент и так входит в любой Swift
тулчейн на Linux (отдельной зависимости нет); обёртки инлайнятся
компилятором C — runtime-оверхеда ноль. Эталонный сетевой стек на
Swift — SwiftNIO — решает ровно эту задачу ровно так же: C-shim
`CNIOLinux` для epoll/eventfd. Мы следуем проверенной конвенции.

## 7. Скрытый бонус: точка портабельности по glibc

glibc-обёртка `epoll_pwait2` появилась в апстриме только в **2.36**.
(На Ubuntu 22.04 с «glibc 2.35» она есть — это бэкпорт дистрибутива:
`nm -D /lib/x86_64-linux-gnu/libc.so.6 | grep epoll_pwait2` находит
символ; на ванильных 2.31–2.35 его нет.) Если когда-нибудь понадобится
запускаться на старых glibc, менять придётся **только** `wrapper.c` —
один вызов заменяется на `syscall(SYS_epoll_pwait2, ...)` с передачей
`sigsetsize` (параметр уже предусмотрен в сигнатуре shim'а именно для
этого). Swift-код не изменится ни на строку. Наличие шва = страховка
совместимости.

## 8. Как перепроверить факты самостоятельно

```bash
# 1) что реально экспортирует Glibc-модуль (пути — для brew-тулчейна;
#    для официального — /usr/lib/swift/...):
TOOL=$(dirname $(dirname $(readlink -f $(which swift))))
grep -c include $TOOL/lib/swift/linux/x86_64/SwiftGlibc.h     # ~188
grep -E "epoll|eventfd|timerfd" $TOOL/lib/swift/linux/x86_64/SwiftGlibc.h  # пусто

# 2) packed-проблема (в любом Swift-файле):
#    MemoryLayout<struct{UInt32;UInt64}>.size == 16, а нужно 12

# 3) есть ли epoll_pwait2 в вашей libc:
nm -D /lib/x86_64-linux-gnu/libc.so.6 | grep epoll_pwait2
```

---

## 9. Когда пересматривать решение

- Swift добавит `packed`-структуры **и** включит `sys/epoll.h` в
  umbrella Glibc (или появится официальный модуль `LinuxIO`) — тогда
  CMIO можно будет свести к нулю механически;
- понадобится поддержка не-Linux POSIX (kqueue) — прослойка, наоборот,
  останется, но наполнится `kqueue`-обёртками по той же схеме.

До тех пор: **C — минимальный шов, закрывающий три конкретных пробела
языка; вся библиотека остаётся Swift.**
